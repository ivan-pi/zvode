## [NEXT] 0.2.0 — Procedural interface (Python layer)

The goal of this release is to provide a standalone `solve_complex_ivp()` function.
Note: the integration loop is implemented in Python rather than compiled C, so
there is still a round-trip through the Python interpreter on every accepted step.
Pushing the loop into C (and enabling fully compiled runs with cfunc callbacks)
is deferred to 0.4.0.

## 0.3.0 — Fortran, build system, and developer sugar

Work in this release is concentrated on the Fortran layer, the CMake build
system, and developer-facing conveniences such as type stubs and validation.

- Add a test that asserts NotImplementedError is raised when in_place=True is
  used with a ctypes or numba cfunc function pointer, so the current compiled-
  callback stub is covered and a regression will fire automatically when 0.4.0
  enables the path.
- Domain checking of arguments in Python; there is some duplication of
  responsibilities, as ZVODE does some checks internally too; doing the checks
  in Python beforehand allows to raise a proper exception.
  Constructor checks are in place (_check_tolerances, _determine_miter, int32
  overflow guards, C-layer array validation on istate==1).  The open question is
  how to cover checks that only become relevant inside _step_impl — one idea is
  to call ZVODE once with the same t and tout (a no-op step) to let ZVODE raise
  ISTATE errors early, but the exact mechanics are still TBD.
- Fix nfev/njev evaluation counters: _validate_fun_shape and _validate_jac_shape
  each call the user callback once at construction time (to probe the return
  shape), but neither call is counted toward nfev / njev.  The Fortran library
  owns those counters inside iwork and they are only readable after an accepted
  step, so incrementing them here would require duplicating the counters in
  Python.  Both probe calls are marked FIXME in _helpers.py.
- Add option to expose ZEWSET and ZWNORM as callback functions
- Provide CMake option to use external BLAS; if not available, fallback to
  vendored procedures
- Ensure implicit none is used and all variables are strictly typed
  (c_zvode.f90 uses implicit none throughout; zvode.f is upstream — not modified)
- Add Python typing hints (the .pyi files)
- Add short docstring Examples sections to ZVODE and solve_complex_ivp
  (a few ``>>>`` lines each; enough for ``help()`` to be useful in a REPL)
- Check older SciPy versions for any bug fixes not yet incorporated, and verify
  original licenses are properly attributed
- Note on NEQ reset: when NEQ is reset during integration (ISTATE = 3), we must
  also modify the NEQ component of fun and jac class instances; not relevant to
  the SciPy interface as neq can't change during integration — document this


## 0.4.0 — Performance: C-layer time-stepping, compiled callbacks, and API hardening

The procedural interface from 0.2.0 calls back into Python once per accepted
step.  This release pushes the integration loop into the C extension and
completes the compiled-callback path (originally planned for 0.2.0), so that
when RHS/Jacobian are compiled the entire run executes without touching the
Python interpreter.

- Lower the time-stepping loop from Python into the C extension layer
  (implement _zvode.drive()):
  - C driver calls c_zvode in a loop, collecting output into pre-allocated
    buffers, and only returns to Python when the endpoint is reached or an
    error occurs
  - When RHS / Jacobian are pure C function pointers (ctypes, cfunc), no GIL
    acquisition is needed during the loop
- Enable compiled callbacks (numba @cfunc, ctypes CFUNCTYPE): wire up the
  fun_addr / jac_addr path in solve_complex_ivp through _zvode.drive(), removing
  the NotImplementedError stub added in 0.2.0
- API hardening: review and stabilise the procedural interface signatures,
  return types, and error reporting ahead of the 1.0.0 API freeze
- Benchmarks: add a small benchmark suite to quantify the overhead reduction
  relative to 0.2.0 and to the OdeSolver interface


## 1.0.0 — Stable release with online documentation

The 1.0.0 milestone signals API stability. The fast procedural interface
completed in 0.4.0 must handle the case where the RHS and Jacobian are fully
compiled (no Python callbacks), so that the entire integration runs in
compiled code without GIL round-trips.

- Procedural interface declared stable (no breaking changes after this point)
- Minimalistic documentation in .rst format, hosted on GitHub Pages
  - Sphinx build configured, GitHub Actions workflow to deploy on each release
  - API reference, user guide, and at least one worked example
- Binary wheel distribution: set up cibuildwheel in CI to publish manylinux
  and macOS wheels to PyPI on each release tag
- Windows wheel builds: add a windows-latest runner to the CI matrix,
  document the required Fortran toolchain (gfortran via MSYS2/mingw-w64 or
  Intel ifx), and add "Operating System :: Microsoft :: Windows" to the
  pyproject.toml classifiers


## Post-1.0 — Future work (no API breaks expected)

These items are intentionally deferred. Thread safety and common-block removal
are internal concerns that should not require any user-visible API changes.

- Thread safety: ZVODE uses process-global Fortran COMMON blocks, so concurrent
  calls from multiple threads will race.  A process-wide Lock (or reentrant
  wrapper) is the correct fix.  Deferred because it requires careful testing
  and adds overhead that single-threaded users should not pay.
- (minor release) Replace COMMON blocks with a Fortran derived type
  encapsulating the integrator state; employ automated refactoring tools for
  this transformation.  This is a prerequisite for true thread safety.
- Python Array-API / cupy support: support execution in the memory spaces of
  other array libraries.
- 64-bit integer build variant (ILP64) for very large systems.


## Out of scope — desirable but not attainable short-term

These features are genuinely useful but are architecturally out of scope for
a binding to the classic ZVODE Fortran solver, or require effort that is
disproportionate to the library's current stage.  They are documented here so
users understand why they are absent and know where to look instead.

- Sparse or matrix-free Jacobians: ZVODE is a dense/banded Adams-BDF solver
  and has never had a sparse path.  Adding this would require replacing the
  underlying solver entirely, e.g. with SUNDIALS CVODE (available via
  scikits.odes or diffrax).  Out of scope for this package.

- Event/root-finding: ZVODE has no built-in root-detection mechanism.
  Implementing it at the Python layer (bisecting between steps) is feasible
  but adds significant complexity.  Users who need event handling today should
  use scipy.integrate.solve_ivp with the events= argument on the equivalent
  doubled real system, or SUNDIALS CVODE.

- Automatic detection of non-analytic stiff RHS: the analytic requirement for
  stiff complex-valued problems (Cauchy-Riemann equations) cannot be checked
  automatically for an arbitrary callable.  Documentation is the correct and
  only feasible response.
