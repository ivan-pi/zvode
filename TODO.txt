## [NEXT] 0.2.0 — Procedural interface

The goal of this release is to provide a standalone `zvode()` function that
drives the entire integration loop in compiled code, avoiding repeated
round-trips through the Python interpreter on every accepted step.

- Add a procedural `zvode()` function:
  - Version A: driver stores the automatically chosen step times
  - Version B: uses ZVINDY to interpolate the solution at caller-supplied t_eval points
- Ensure that when the RHS callback (and Jacobian) are compiled (e.g. via
  numba @cfunc, ctypes, or Cython), no Python frames are entered during integration
- Document the ZVINDY COMMON block constraint: ZVINDY is only valid immediately
  after a step on the same ZVODE instance; make this explicit in the API
- Check older SciPy versions for any bug fixes not yet incorporated, and verify
  original licenses are properly attributed
- Mention the ZVODE rewrite in C and point to the (older) scipy ode integrator
  that wraps ZVODE (https://docs.scipy.org/doc/scipy/reference/generated/scipy.integrate.ode.html)


## 0.3.0 — Argument validation and optional callbacks

- Domain checking of arguments in Python; there is some duplication of
  responsibilities, as ZVODE does some checks internally too; doing the checks
  in Python beforehand allows to raise a proper exception.
  Constructor checks are in place (_check_tolerances, _determine_miter, int32
  overflow guards, C-layer array validation on istate==1).  The open question is
  how to cover checks that only become relevant inside _step_impl — one idea is
  to call ZVODE once with the same t and tout (a no-op step) to let ZVODE raise
  ISTATE errors early, but the exact mechanics are still TBD.
- Add option to expose ZEWSET and ZWNORM as callback functions
- Provide CMake option to use external BLAS; if not available, fallback to
  vendored procedures
- Ensure implicit none is used and all variables are strictly typed
  (c_zvode.f90 uses implicit none throughout; zvode.f is upstream — not modified)
- Add Python typing hints (the .pyi files)
- Note on NEQ reset: when NEQ is reset during integration (ISTATE = 3), we must
  also modify the NEQ component of fun and jac class instances; not relevant to
  the SciPy interface as neq can't change during integration — document this


## 1.0.0 — Stable release with online documentation

The 1.0.0 milestone signals API stability. The fast procedural interface
introduced in 0.2.0 must be complete and handle the case where the RHS and
Jacobian are fully compiled (no Python callbacks), so that the entire
integration runs in compiled code without GIL round-trips.

- Fast procedural interface complete and stable:
  - Compiled-callback path verified (numba @cfunc, ctypes, or Cython)
  - ZVINDY interpolation path stable and documented
- Minimalistic documentation in .rst format, hosted on GitHub Pages
- Support for Python Array-API interface (cupy?) noted as a known gap or
  stub, with a clear message if a non-NumPy array is passed
- 64-bit integer version (LP64 vs ILP64) assessed; decision documented


## Post-1.0 — Future work (no API breaks expected)

These items are intentionally deferred. Thread safety and common-block removal
are internal concerns that should not require any user-visible API changes.

- Thread safety: ZVODE uses process-global Fortran COMMON blocks, so concurrent
  calls from multiple threads will race.  A process-wide Lock (or reentrant
  wrapper) is the correct fix.  Deferred because it requires careful testing
  and adds overhead that single-threaded users should not pay.
- (minor release) Replace COMMON blocks with a Fortran derived type
  encapsulating the integrator state; employ automated refactoring tools for
  this transformation.  This is a prerequisite for true thread safety.
- Python Array-API / cupy support: support execution in the memory spaces of
  other array libraries.
- 64-bit integer build variant (ILP64) for very large systems.
